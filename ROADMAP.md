# БЛОК A. Платформа для агентной разработки

## Этап A1 — Монорепо *(фундамент, ~1–2 сессии)*

**Цель (из требования 1):** объединить `docs + backend + frontend` в один репозиторий,
чтобы агент видел весь контекст и вертикальный слайс делался в одном PR.

### A1.1 Слияние репозиториев с сохранением истории
1. Создать новый **приватный** репозиторий `biologic-app/biologic` (монорепо).
2. Влить оба существующих репо, **сохранив git-историю**, через `git subtree add`
   (или `git filter-repo --to-subdirectory-filter`) в поддиректории `backend/` и
   `frontend/`. Не терять теги/ветки.
3. Целевая раскладка:
   ```
   biologic/
   ├── backend/            # FastAPI, uv, Python 3.11
   ├── frontend/           # Vue 3, bun
   ├── docs/               # единая документация (см. Этап A2)
   ├── .github/workflows/  # CI (см. A1.4)
   ├── .claude/            # скиллы, агенты, настройки
   ├── Makefile / justfile # оркестрация обеих подсистем
   └── .pre-commit-config.yaml
   ```
4. Перенести правила из трёх `CLAUDE.md`/`AGENTS.md` в один корневой + подпапочные;
   **отменить правило «два репо, раздельные коммиты»** — теперь один репо, коммиты
   могут (но не обязаны) трогать обе стороны; для вертикального слайса — один PR.
5. Архивировать старые репозитории (read-only) со ссылкой на монорепо.

> **Решено (2026-07-09):** приватный `biologic-app/biologic`, subtree-слияние с сохранением
> истории. Перенести CI-секреты старых репо в новый.

### A1.2 Скиллы проекта (требование 1.1)
Зафиксировать в `.claude/` монорепо набор: **codebase-memory**, **nuxt-ui**,
**playwright-cli**, **k6-scenario-authoring** (+ `k6-flow-authoring`). Переиндексировать
codebase-memory на новый корень монорепо (сейчас индексы указывают на старые пути).

### A1.3 Единый тулинг: форматтеры/линтеры (требование 1.3)
- **Backend (без изменений инструментов):** `uv`, `ruff` (format+check), `mypy`.
- **Frontend (без изменений):** `bun`, `eslint`, `vue-tsc`.
- **Оркестрация монорепы:**
  - корневой `Makefile`/`justfile`: `make lint` = backend ruff/mypy + frontend eslint/tsc;
    `make format`, `make test`, `make e2e`;
  - единый `.pre-commit-config.yaml` с хуками обеих подсистем (образец — `.pre-commit-config.yaml`
    в staraudio), scoped по путям;
  - `.editorconfig` в корне (LF, utf-8; 2 пробела FE / 4 BE).

### A1.4 CI-пайплайн на GitHub (требование 1.2) + e2e-шаблоны из staraudio
`.github/workflows/ci.yml` с **path-фильтрами** (backend-джобы на `backend/**`,
frontend — на `frontend/**`), образец — `staraudio-backend/.github/workflows/ci.yml`
(джоб на заботу, `concurrency`+`cancel-in-progress`, таймауты, артефакты `if: always()`):

| Джоб | Триггер | Что делает |
|---|---|---|
| `be-lint` | `backend/**` | `uv sync` → ruff + mypy |
| `be-tests` | `backend/**` | Postgres 15 → `alembic upgrade head` → `make test` |
| `be-migrations` | `backend/**` | `alembic upgrade head` + `alembic check` (дрейф ORM↔миграции) |
| `fe-quality` | `frontend/**` | `bun install --frozen-lockfile` → eslint → vue-tsc |
| `fe-build` | `frontend/**` | `bun run build` |
| `sdk-contract` | `backend/** \| frontend/**` | поднять backend → `bun run sdk:generate` → упасть, если SDK-diff не пуст |
| `e2e` | both | стенд (PG+миграции+seed+uvicorn+собранный SPA) → Playwright + k6 → артефакты |

Скопировать/адаптировать e2e-инфраструктуру staraudio: `tests/k6/{helper,scenarios}`,
`scripts/k6_report_visual`, кастомный k6-Dockerfile (xk6), `docker-compose.test.yml`,
профили `K6_PROFILE`.

**DoD A1:** один репозиторий с сохранённой историей; `make lint/test` зелёные для обеих
подсистем; PR прогоняет path-фильтрованный CI; codebase-memory переиндексирован.

## Этап A2 — Документация проекта (требование 2, ~2–3 сессии)

**Цель:** единая, машиночитаемая база знаний, из которой агент берёт контекст для фич.
За основу — материалы из NotebookLM (владелец) + существующие
`role-access-matrix.md`, `frontend-user-stories.md`, `work-processes-by-roles.md`.

### A2.1 Диаграмма действий пользователей + карта автоматизации
- **Диаграмма** (mermaid/BPMN в `docs/processes/user-actions.md`): все сценарии всех
  ролей от приёмки материала до выдачи протокола (сквозной поток направление → образцы →
  исследования → тесты → протокол → выписка).
- **Карта автоматизации** — по каждому шагу пометка:
  - 🟦 автоматизируется **старой программой** (что легаси уже делает);
  - 🟩 **потенциально автоматизируемо** новой системой (кандидат на фичу);
  - ⬜ ручное, автоматизация нецелесообразна.
  - Это прямой источник приоритетов для Блока C.

### A2.2 Документация по действиям каждой роли (требование 2.1)
Отдельный документ на роль в `docs/roles/` (расширить `role-access-matrix.md` до
процессных описаний «что делает и зачем»): **Регистратор, Санитарный врач,
Ассистент лаборатории (АЛ), Врач-лаборант (ВЛ), Начальник лаборатории (НЛ),
Начальник филиала (НФ), Администратор пользователей (АП)**. Для каждой роли: реестр
действий, ресурсы/статусные переходы (сверить с `role-access-matrix.md`), сценарии,
критерии готовности. Это спецификация, по которой пишутся вертикальные слайсы Блока C.

### A2.3 Скрытая обратная связь: телеметрия интерфейса (требование 2.2)
Механизм пассивного логирования действий пользователя для последующего анализа UX:
- **Frontend:** директива/composable, перехватывающая события (клики, навигация,
  открытие модалок, отправка форм, ошибки) — `{ event, element_id/data-telemetry,
  route, role, ts, session_id }`; буфер + батч-отправка fire-and-forget; выключаемо флагом.
- **Backend:** эндпоинт приёма (`POST /telemetry/events`, батч), таблица `ui_events`
  (партиционируемая по дате), без чувствительных данных (только идентификаторы элементов).
- **Аналитика:** заготовка запросов/дашборда (какие экраны/действия «залипают»,
  где ошибки, воронки по ролям). Пометить приватность: анонимно, retention-политика.
- Разметить ключевые элементы `data-telemetry="..."` по мере разработки фич Блока C.

**DoD A2:** диаграмма действий с картой автоматизации; 7 ролевых документов; работающая
телеметрия (события долетают в БД) с примером аналитического запроса.

## Этап A3 — Пайплайн создания фич (требование 3, ~1–2 сессии на наладку)

**Цель:** воспроизводимый агентный конвейер «issue → вертикальный слайс → видео».
**Триггер задачи — детально оформленный GitHub issue.**

### A3.1 Шаблоны и артефакты
- GitHub **issue template** для фичи/багфикса: контекст, роль, acceptance criteria,
  затрагиваемые экраны/эндпоинты, ссылки на docs/диаграмму.
- **PR template**: чек-лист (план/верификация/тесты/линт/SDK-regen/видео).
- `docs/features/<slug>/` staged-скаффолд (скилл `feature-generator`,
  `01-planning…05-testing`) — образец из staraudio.

### A3.2 Стадии конвейера (каждая — с явным выходным артефактом)
1. **План** — исследование кодовой базы (codebase-memory) и документации → план вертикального
   слайса (FE↔BE), файл-уровень.
2. **Верификация плана (итеративно)** — blast radius: что может сломаться, оценка
   архитектурных решений; правки плана до схождения. *(агент: `feature-planner`/`critic`)*
3. **Имплементация** — вертикальный слайс backend→SDK→frontend. *(агент: `ddd-executor`/`executor`)*
4. **e2e в изолированной среде** — k6 (API-контракт) + Playwright (UI) на отдельном
   стенде/worktree. *(скиллы `k6-*-authoring`, `playwright-cli`)*
5. **CI + PR** — линтеры, тесты, sdk-contract на GitHub; открыть PR.
6. **Цикл починки PR** — пока красный CI не станет зелёным (повтор 3–5).
7. **Ревью другой моделью** — независимая проверка, в т.ч. **что старые тесты реальные**
   (не подогнаны/не заглушены). *(агент `code-reviewer`; либо `/code-review ultra`)*
8. **Видео** — запись демо: **ДО и ПОСЛЕ** для багфикса, **только ПОСЛЕ** для нового
   функционала. *(скилл `flow-video-recorder` во frontend — уже есть)*

### A3.3 Автоматизация конвейера
Оформить как переиспользуемый workflow/скилл поверх OMC (`autopilot`/`team`) + GitHub
Actions на события issue/PR. Зафиксировать в `docs/processes/feature-pipeline.md`.

**DoD A3:** одна реальная фича проведена сквозь все 8 стадий как эталон; шаблоны issue/PR
в репо; видео ДО/ПОСЛЕ приложено к PR.

# БЛОК C. Продуктовый функционал (вертикальные слайсы)

> Все фичи идут через конвейер A3. Приоритет — по карте автоматизации A2.1.
> Статусы образца: `pending→registered→in_progress→analyzed→completed`, `rejected`.
> «Выпустить образец» = `analyzed→completed` (команда `close`); «Браковать» = `rejected` (`reject`).

## Этап C1 — Функционал регистратора (требование 4, ~4–6 сессий)

### C1.1 Пошаговый импорт направлений *(ключевая фича)*
- Импорт из файла с **авто-привязкой санитарного врача**: подбор из существующих по
  данным файла, либо создание нового прямо в процессе; аналогично **выбор объекта** из
  списка или создание нового.
- **UI — пошаговый мастер (wizard):** регистратор идёт по образцам направления и вручную
  проставляет типы/поля, переходя образец-за-образцом (а не одна огромная форма) —
  ключ к скорости. Backend: анализ `legacy_direction_import.py` + `direction_sample_import.py`,
  расширить summary (`import_warnings`) до пошаговых замечаний по каждому образцу.

### C1.2 Пошаговое ручное создание направления
При ручном создании — сразу добавлять образцы без лишних переходов, тем же
пошаговым процессом (переиспользовать wizard из C1.1). Учесть текущий lockdown прямого
создания (nested-создание образцов уже влито в бэкенд).

### C1.3 Фильтрация по направлениям/образцам *(тест + доведение)*
Протестировать и починить существующую фильтрацию (frontend `filters-search.spec.ts`
уже есть; расширить e2e). Сверить контракт фильтров BE↔FE.

### C1.4 Окно «выпущенные образцы по направлениям»
Экран: выпущенные образцы, **сгруппированные по направлениям**, с отображением статуса
остальных образцов направления. **Если все образцы направления выпущены — направление
подсвечивается жёлтым.** Backend: read-проекция (агрегат по направлению: выпущено/всего +
флаг «все выпущены»); FR: цветовая индикация. Разметить `data-telemetry` (A2.3).

### C1.5 Массовая регистрация с детальными ошибками
Регистрация нескольких направлений/образцов разом; при ошибке — **детальная причина по
каждой записи** + переход к пошаговому процессу заполнения/правки с **подсветкой
невалидных полей**. Backend: per-item результат в ответе команды (успех/ошибка+поле+причина).

**DoD C1:** wizard импорта и ручного создания работают пошагово; фильтрация покрыта e2e;
окно группировки с жёлтой подсветкой; массовая регистрация возвращает адресные ошибки и
ведёт к правке с подсветкой полей. Видео ПОСЛЕ по каждой фиче.

## Этап C2 — Функционал врача-лаборанта / ВЛ (требование 5, ~2–3 сессии)

- **Браковать образец** — команда `reject` (обязательная причина). Уже в контракте (US §4).
- **Проставлять показатели** для целей исследования образца + **комментарии** к образцу,
  которые пойдут в протокол — команды над тестами (`complete`: `value`/`norm`/`comment`;
  US §6) и/или поле комментария образца, попадающее в проекцию протокола.
- **Выпускать образец** — команда `close` (`analyzed→completed`, вердикт; US §4).

**DoD C2:** ВЛ проводит образец через брак/показатели/выпуск на реальном API; комментарии
попадают в данные протокола; покрыто k6 + Playwright.

## Этап C3 — Функционал начальника лаборатории / НЛ (требование 6, ~2–3 сессии)

- **Всё то же, что у ВЛ** (переиспользовать C2).
- **Пост-выпуск редактирование** показателей/тестов после выпуска образца, с
  **обязательной отметкой в аудите** (`change_log`) — новая команда + запись в аудит
  с указанием актора/до/после.
- **Управление показателями и целями исследования** (`indicators`, `research_goals`)
  **в рамках своей лаборатории** — CRUD со scope `own_lab`. В MVP ограничение «своя
  лаборатория» — на **фронте** (решение B1); жёсткий серверный scope-энфорсмент —
  в этапе **D5** (до него компромисс задокументирован).

**DoD C3:** НЛ выполняет действия ВЛ; правка после выпуска фиксируется в аудите; CRUD
показателей/целей ограничен своей лабораторией на UI (серверная гарантия — в D5).

## Этап C4 — Протоколы, выписка, подпись (требование 4, ~4–5 сессий)

### C4.1 Формирование РЕАЛЬНОГО протокола из xlsx
- **Исходники и шаблоны старой программы доступны** (подтверждено владельцем 2026-07-09) —

  формулы, откуда берёт показатели. Результат — `docs/processes/legacy-protocol.md`.
- Реализовать генерацию протокола по шаблону xlsx на основе данных образцов/тестов/

### C4.2 Выписка из протокола (бракованные образцы)
Формирование **выписки** на основе шаблона, куда входят **бракованные** образцы —

### C4.3 Электронная подпись *(опционально/исследование)*
Потенциально — эл.подпись протокола начлабами (НЛ) и начцентра. Отдельный research-этап:
выбрать механизм (крипто-провайдер/сертификаты/облачная подпись), правовые требования,
хранение подписанных документов. **Не блокирует C4.1–C4.2.**

**DoD C4:** протокол генерируется из реальных данных по xlsx-шаблону, совпадает с

# БЛОК D. Технический долг (параллельный трек, по мере надобности)

Не блокирует продукт, но снижает стоимость изменений. Брать между продуктовыми слайсами.

- **D1. Финал DDD-консолидации** (`backend-architecture-review.md` «шаги перехода»):
  `DomainEvent`/`StatusChanged` → `core/events.py` (уже частично: `src/core/events.py` есть),
  `EventBus`-порт, усилить `test_architecture_boundaries`, разрезать `entities.py` по модулям,
  перенести `laboratory_workflow`/`notifications` из `src/contexts/`. Контракт не меняется.
- **D2. Выравнивание модели данных** (`schema-vs-backend-diff.md`): партиал-индекс
  `user_scopes`, вердикты по расхождениям, пересборка документа данных.
- **D3. Фронтенд-рефакторинг −3500 LOC** (`frontend-refactor-plan.md` Phase 2–6): удаление
  мёртвого кода, унификация инфраструктуры, фикс багов таблиц, декомпозиция god-компонентов,
  i18n. Делать по мере касания соответствующих экранов в Блоке C.
- **D4. Observability и эксплуатация** (образцы staraudio): `/health`+`/ready`, request-id +
  JSON-логи, Sentry/GlitchTip, nightly (`e2e-nightly.yml`, `K6_PROFILE=load`), prod-compose
  (uvicorn+`APP_STATIC_DIR`+PG-volume), бэкап БД, `make audit` в CI.
- **D5. Серверный RBAC scope-энфорсмент** *(решено выносом из B1)*: scope-фильтрация на
  бэкенде по `role-access-matrix.md` (own/own_lab/own_branch/all_labs/all_branches/all;
  сноски $^1..^7$) — фильтры в репозиториях по актору/скоупу + негативные тесты (роль вне
  scope → 403/404). Закрывает MVP-компромисс «своя лаборатория только на FE» из C3.
  Делать после того, как ролевой функционал (C1–C3) стабилизируется.

## Сводная последовательность и зависимости

```
A1 Монорепо ─────────────┐ (фундамент; отменяет «два репо»)
A2 Документация+телеметрия├─ параллельно, но A2.1 карта автоматизации задаёт приоритет C
A3 Пайплайн фич ──────────┘ (эталонная фича прогоняется на B1 или C1)
                 │
B1 Аутентификация+RBAC ── prerequisite для всех ролевых фич
                 │
C1 Регистратор ──┐
C2 Врач-лаборант ├─ вертикальные слайсы через конвейер A3, приоритет по карте A2.1
C3 Начлаб        │   (own_lab в MVP — на FE; серверная гарантия — в D5)
C4 Протоколы     ┘
                 │
D1–D5 Техдолг ── параллельно, между слайсами (D5 = серверный RBAC, после C1–C3)
```

**Рекомендуемый старт:** A1 (монорепо) → A3 (наладить конвейер) на маленькой фиче →
B1 (авторизация) → C1 (регистратор) как первый крупный вертикальный слайс, попутно
A2 (документация задаёт приоритеты) и D-долг по касанию.

**Правила (обновлены под монорепо):** один репозиторий, вертикальный слайс = один PR
через issue-триггер; Conventional Commits (англ., ≤72); backend — `uv`/`make` (Python 3.11),
frontend — `bun`; изменение API ⇒ SDK-regen — часть DoD; коммит/пуш — по явной просьбе.
