# Словарь терминов проекта

Единый глоссарий предметной области LIMS Biologic — для онбординга новых
разработчиков и продуктовой команды. Термины сгруппированы по доменам;
внутри группы — по алфавиту. Русский термин указан с английским
ключом/полем в коде там, где это уместно, и со ссылкой на исходники или
ролевые/процессные документы.

## Рабочие объекты (жизненный цикл лаборатории)

- **Направление** (`Direction`, таблица `directions`) — сущность верхнего
  уровня жизненного цикла: заявка на исследование партии образцов от
  санитарного врача с объекта. Содержит список образцов, объект, врача,
  даты сбора/доставки. Жизненный цикл статусов: `draft → registered →
  in_progress → partially_completed → completed`. См.
  `roles/registrar.md`, `product/statuses.md`.
- **Образец** (`Sample`, таблица `samples`) — единица материала внутри
  направления, над которой выполняются исследования. Жизненный цикл:
  `pending → registered → in_progress → analyzed → completed`; терминальная
  ветка `→ rejected` (брак) из `pending`/`registered`/`in_progress`; после
  `analyzed` возможен возврат `→ in_progress` при назначении новых
  исследований. См. `product/statuses.md`.
- **Исследование** (`Research`, таблица `research`, также встречается как
  `results` на бэкенде) — единица работы по конкретной цели исследования
  для одного образца, назначается регистратором и подтверждается
  врачом-лаборантом. Статусы: `draft → ordered → in_progress → completed`;
  `draft`/`ordered → rejected`. См. `roles/lab-doctor.md`.
- **Испытание / тест** (`Test`, таблица `tests`) — измерение по одному
  показателю (`indicator`) внутри исследования; создаётся автоматически при
  назначении исследования (по одной строке на каждый показатель цели).
  Статусы: `queued → in_progress → completed`; `queued`/`in_progress →
  rejected`; `in_progress → queued` (вернуть в очередь). После завершения
  всех испытаний исследования оно автоматически переходит в `completed`
  (каскад, не отдельная команда). См. `roles/lab-doctor.md`,
  `frontend/flows/lab-doctor.flow.md` §4.
- **Цель исследования** (`ResearchGoal`, таблица `research_goals`) —
  справочник типовых наборов показателей, которые проверяются в рамках
  одного исследования (например, «бактериологический анализ»); связывает
  исследование со списком `indicators`. Ведётся начальником лаборатории
  (`lab_chief`) в рамках своей лаборатории. См. `roles/lab-chief.md`.
- **Показатель** (`Indicator`, таблица `indicators`) — конкретная измеряемая
  величина внутри цели исследования (например, «КМАФАнМ», «БГКП»), с
  нормой сравнения. По каждому показателю цели создаётся одно испытание
  (`test`). Ведётся начальником лаборатории. См. `roles/lab-chief.md`.
- **Протокол** (`Protocol`, таблица `protocols`) — командная сущность,
  объединяющая N завершённых (`sample_statuses.code = completed`) образцов
  одного направления в единый выпускаемый документ с заключением. Создаётся
  только регистратором (`POST /protocols`), не является плоской
  CRUD-записью. Поддерживает выдачу (`issue`) с проставлением `issued_at`.
  См. `roles/registrar.md`, `frontend/flows/registrator.flow.md` §16-17.
- **Выписка / выпуск образца** — закрытие образца начальником лаборатории
  (`analyzed → completed`) с установкой финального вердикта — образец
  считается выпущенным из лабораторного процесса. См. `roles/lab-chief.md`.
- **Брак** (`rejected`) — терминальный статус образца/исследования/
  испытания, означающий, что материал или измерение признаны непригодными.
  Брак образца каскадно переводит в `rejected` все его незавершённые
  исследования (`cancellation_reason = 'sample_rejected'`). См.
  `product/statuses.md`, раздел «Каскадные эффекты».
- **Вердикт** (`verdict`) — итоговое заключение по образцу
  («соответствует» / «не соответствует»), устанавливается начальником
  лаборатории при закрытии образца (`analyzed → completed`). См.
  `roles/lab-chief.md`.
- **Заключение** (`Conclusion`, справочник `conclusions`) — типовая
  формулировка вывода для протокола (например, «Соответствует требованиям»,
  «Не соответствует требованиям»); выбирается из справочника при создании
  протокола вместо свободного текста. Ведётся регистратором в рамках
  филиала. Засеяно миграцией `20260702_0016_seed_conclusions`. См.
  `frontend/flows/registrator.flow.md` §16.
- **Дедлайн** (`deadline`) — расчётный срок выполнения по образцу/
  направлению; вычисляется системой при регистрации образца
  (`received_at` + нормативный срок). Просроченные дедлайны — источник
  критических уведомлений для нескольких ролей.

## Статусы жизненного цикла (авторитетный источник — `src/core/status_codes.py`)

```
DIRECTION: draft → registered → in_progress → partially_completed → completed
SAMPLE:    pending → registered → in_progress → analyzed → completed
           pending/registered/in_progress → rejected;  analyzed → in_progress (reopen)
RESEARCH:  draft → ordered → in_progress → completed
           draft/ordered → rejected
TEST:      queued → in_progress → completed
           queued/in_progress → rejected;  in_progress → queued (requeue)
```

Стабильные `code`-строки статусов (`draft`, `registered`, …) — авторитет для
UI и статусных переходов; лайфсайкл-сущности ссылаются на статус-таблицы
(`direction_statuses`, `sample_statuses`, `research_statuses`,
`test_statuses`) по UUID. Правила допустимых переходов —
`backend/src/contexts/laboratory_workflow/domain/status_policy.py`, подробное
описание с инициаторами и комментариями — `product/statuses.md`.

## Организационная структура

- **Объект** (`Object`, справочник `objects`) — предприятие/точка, с
  которой санитарный врач собирает образцы (например, пищевое производство,
  столовая). Закреплён за филиалом; в перспективе — и за конкретным
  санитарным врачом (`own_objects` scope, см. «Известные ограничения» в
  `roles/sanitary-inspector.md`). Ведётся регистратором.
- **Филиал** (`Branch`, справочник `branches`) — территориальное
  подразделение лаборатории; единица области видимости `own_branch` для
  большинства операционных ролей. Возглавляется начальником филиала
  (`branch_chief`).
- **Лаборатория** (`Lab`, справочник `labs`) — подразделение внутри
  филиала, выполняющее конкретные виды исследований; единица области
  видимости `own_lab` для ролей врача-лаборанта, ассистента и начальника
  лаборатории. Направление/образец назначается на лабораторию через
  `assign-research`.
- **Врач** (`Doctor`, справочник, поле `doctor_id` направления) — санитарный
  врач, указанный как автор/ответственный за направление (используется как
  ссылка на владельца направления при резолвинге получателя уведомлений
  через `Direction.created_by`, а не напрямую).

## Роли и доступ (RBAC)

- **Роль** (`Role`, таблица `roles`) — именованный набор прав пользователя.
  7 функциональных ролей проекта задокументированы в `roles/` — см. таблицу
  в `roles/README.md`; плюс техническая роль `developer` (для разработки/
  отладки, вне ролевых документов).
- **Право / разрешение** (`Permission`, таблицы `permissions`,
  `role_permissions`) — пара «ресурс × действие» (например,
  `directions:register`), опционально с признаком `scope`. Полная матрица —
  `product/role-access-matrix.md`.
- **Скоуп / область видимости** (`scope`, таблица `user_scopes`) —
  ограничение видимости данных пользователя по организационной иерархии:
  - **own** — только записи, созданные/адресованные самому пользователю
    (например, свои уведомления, «свои» направления санитарного врача);
  - **own_lab** — в рамках своей лаборатории (врач-лаборант, ассистент,
    начальник лаборатории);
  - **own_branch** — в рамках своего филиала (регистратор, администратор
    пользователей, по умолчанию — начальник филиала);
  - **all** — без ограничения (полный доступ; настраивается индивидуально
    для начальника филиала через `user_scopes`, полный — у роли
    `developer`).
  Практическая реализация автоматического скоупинга в списках сейчас
  ограничена (см. разделы «Границы (scope)» в документах `roles/*.md`) —
  сужение сегодня в основном ручное, через фильтры UI.
- **Пользователь** (`User`, таблица `users`) — учётная запись сотрудника:
  логин, ФИО, роль, привязка к лаборатории, флаги `is_registrar` /
  `is_lab_head` / `is_branch_head`. Управляется администратором
  пользователей (`user_admin`).
- **Переопределение права** (`PermissionOverride`) — персональное allow/deny
  поверх прав роли для конкретного пользователя. См.
  `product/frontend-user-stories.md`, раздел 8.
- **Команда** (в контексте API) — операция изменения состояния сущности
  через `POST /{resource}/{id}/{action}` (например, `register`, `confirm`,
  `reject`), в отличие от CRUD-операций (`GET`/`POST`/`PATCH`/`DELETE`).
  Смена статуса жизненного цикла выполняется только через команды, никогда
  через `PATCH status_id`. См. корневой `CLAUDE.md`, раздел «API Design».

## Аудит и уведомления

- **Аудит / технический аудит** (`change_log`, ресурс `history`) — журнал
  всех изменений сущностей: `{ action, actor_name, diff, snapshot,
  created_at }`, доступен через `GET /history?filters={entity_type,
  entity_id}`. Отображается на вкладке «Технический аудит» в карточках
  направлений/образцов/исследований/протоколов. Отдельно от «бизнес-статуса»
  (степпер перехода статусов в карточке).
- **Уведомление / алерт** (`Alert`, ресурс `alerts`) — системное сообщение о
  событии (брак образца, приближающийся дедлайн, готовый протокол и т. д.),
  доставляется в реальном времени по SSE (`GET /alerts/stream`,
  `event: notification.created`) и адресуется конкретному пользователю
  (обычно — владельцу/автору направления, `Direction.created_by`).
  Действие «отметить прочитанным» — `POST /alerts/{id}/mark-read`; действие
  «скрыть» задокументировано, но не реализовано (см. известные ограничения
  в `roles/sanitary-inspector.md`).
- **Событие / доменное событие** (`SampleRejected` и т. п.,
  `backend/src/core/events.py`) — внутреннее событие домена, публикуемое при
  командных переходах статусов; обрабатывается подписчиками (например,
  `WorkflowNotificationSubscriber`), которые создают уведомления в той же
  транзакции, что и сама команда.

## Справочники (catalogs)

Общий термин для CRUD-управляемых наборов ссылочных данных, доступных в
разделе «Справочники» (`/dictionaries/:module?`): объекты, типы образцов,
филиалы, врачи, лаборатории, цели исследований, показатели, заключения,
типы протоколов, статусы (4 контекста — для направлений/образцов/
исследований/тестов). См. `product/frontend-user-stories.md`, раздел 7.

## Технические термины (архитектура/контракт)

- **DDD-контекст / bounded context** — модуль предметной логики backend'а
  (`laboratory_workflow`, `catalogs`, `access_control`, `audit`,
  `notifications`, `dashboard`), см. корневой `CLAUDE.md`, раздел «DDD
  Bounded Contexts».
- **OpenAPI-контракт** — граница между backend и frontend; единственный
  канал взаимодействия — HTTP API по сгенерированной из `/openapi.json`
  схеме (`bun run sdk:generate`). Прямой импорт кода между подсистемами
  запрещён. См. корневой `CLAUDE.md`, раздел «Контракт: OpenAPI».
- **Проблемные детали / Problem Details** (`application/problem+json`) —
  формат ошибок API (`AppError`, `NotFoundError`, `BadRequestError`,
  `ValidationError`, `DomainConflictError`, `UnauthorizedError`,
  `ForbiddenError`). См. корневой `CLAUDE.md`, раздел «Errors».
