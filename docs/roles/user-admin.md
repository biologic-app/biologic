# Администратор пользователей (user_admin)

## Назначение
Администратор пользователей управляет учётными записями сотрудников: заводит
пользователей, назначает роли, настраивает области видимости (`user_scopes`,
привязку к филиалам и лабораториям) и управляет самими ролями и наборами
разрешений. Роль **не имеет доступа** к операционным данным лаборатории
(направления, образцы, исследования, протоколы) и к лабораторным справочникам.

## Действия

| Действие | Ресурс | Право | Scope | Статусный переход |
|---|---|---|---|---|
| Управление пользователями | `users` | `create` / `read` / `update` / `delete` (C,R,U,D) | own_branch³ | — |
| Управление ролями | `roles` | `create` / `read` / `update` / `delete` (C,R,U,D) | own_branch³ | — |
| Настройка областей видимости пользователей | `user_scopes` | `create` / `read` / `update` / `delete` (C,R,U,D) | own_branch³ | — |
| Управление правами ролей | `role_permissions` | `create` / `read` / `update` / `delete` (C,R,U,D) | own_branch³ | — |
| Просмотр справочника разрешений | `permissions` | `create` / `read` / `update` / `delete` (C,R,U,D) | own_branch³ | — |

> Легенда: ³ = «в рамках своего филиала» (`../product/role-access-matrix.md`).
> Ни один операционный ресурс (`directions`, `samples`, `research`, `tests`,
> `protocols`, `objects`, `indicators`, `research_goals`) администратору
> пользователей **не доступен** — в матрице стоит `—` по всем этим строкам.

## Сценарии

Разделы UI — `/access/users` и `/access/roles`
(см. `../product/frontend-user-stories.md`, разделы 8 «Доступ: Пользователи»
и 9 «Доступ: Роли и права»).

1. Заводит нового пользователя: логин, ФИО, роль (`role_id`), лаборатория
   (`lab_id`), флаги (`is_registrar` / `is_lab_head` / `is_branch_head`),
   пароль.
2. Настраивает область видимости (`user_scopes`) — привязывает пользователя к
   филиалу и/или лаборатории.
3. При необходимости назначает персональное переопределение права
   (`PermissionOverride`) поверх прав роли — allow/deny для конкретного
   пользователя.
4. Управляет ролями: создаёт роль, настраивает матрицу прав `ресурс ×
   действие` (CRUD-права и командные права: `import` / `export` / `register` /
   `confirm` / `start` / `complete` / `close` / `release` / `reject` /
   `requeue` / `approve`).
5. Удаляет пользователя или роль с возможностью отмены (undo) в течение
   короткого таймаута.

## Границы (scope)
Администратор пользователей действует **в рамках своего филиала**
(`own_branch`) применительно к управлению учётными записями и ролями.
**Не имеет доступа** к операционным данным лаборатории и к лабораторным
справочникам — ведение `objects` — зона регистратора, `indicators` /
`research_goals` — зона начальника лаборатории.

> ⚠️ **(уточнить, известное ограничение реализации):** согласно
> `../product/frontend-user-stories.md` (раздел 8, Notes), проверка прав
> (`can()`) на странице пользователей на момент написания документа
> **всегда возвращает `true`** — UI-гейтинг (иконки замка, `disabled`,
> тултипы) реализован, но фактически не ограничивает; целевое поведение
> описано в acceptance criteria, ограничение бэкендом — вне текущего объёма.

## Definition of Done
- Создание, редактирование и удаление (с undo) пользователя работают на
  реальном API; список пользователей использует серверную пагинацию.
- Просмотр прав пользователя показывает права роли и персональные
  переопределения раздельно.
- Создание роли и редактирование матрицы прав (`resource` × `action`,
  опционально `scope`) сохраняются и корректно проецируются на UI-гейтинг
  других ролей.
- `bun run lint typecheck build` зелёные; сценарий проверен на реальном API —
  см. разделы 8 «Доступ: Пользователи» и 9 «Доступ: Роли и права» в
  `../product/frontend-user-stories.md`.
