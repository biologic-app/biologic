# Регистратор (registrar)

## Назначение
Регистратор — первая точка входа образцов и направлений в лабораторную систему.
Он принимает физический материал и электронное направление от санитарного врача
(либо создаёт направление вручную), регистрирует образцы, назначает им типы и
исследования, ведёт справочник объектов своего филиала и формирует протоколы и
заключения по завершённым образцам.

## Действия

| Действие | Ресурс | Право | Scope | Статусный переход |
|---|---|---|---|---|
| Импортировать направление (Excel / JSON / legacy `.xls`) | `directions` | `import` (IMP) | own_branch | — → `draft` |
| Создать направление вручную | `directions` | `create` (C) | own_branch | — → `draft` |
| Редактировать направление | `directions` | `update` (U) | own_branch, только пока `draft` | — |
| Зарегистрировать направление | `directions` | `register` (REG) | own_branch, только из `draft` | `draft` → `registered` |
| Просмотреть направления | `directions` | `read` (R) | own_branch | — |
| Создать образец (в рамках направления) | `samples` | `create` (C) | own_branch | — → `pending` |
| Редактировать образец | `samples` | `update` (U) | own_branch, только пока `pending` | — |
| Зарегистрировать образец | `samples` | `register` (REG) | own_branch, только из `pending` | `pending` → `registered` |
| Забраковать образец (брак при приёмке) | `samples` | `reject` (REJ) | own_branch | `pending` / `registered` / `in_progress` → `rejected` |
| Назначить исследование образцу | `research` | `create` (C) | own_branch | — → `draft` |
| Отклонить исследование (убрать из направления) | `research` | `reject` (REJ) | own_branch | `draft` → `rejected` |
| Просмотреть исследования | `research` | `read` (R) | own_branch | — |
| Создать протокол (по завершённым образцам одного направления) | `protocols` | `create` (C) | own_branch | — |
| Редактировать / просматривать протокол | `protocols` | `update`, `read` (U, R) | own_branch | — |
| Вести справочник объектов | `objects` | `create` / `read` / `update` (C, R, U) | own_branch | — |
| Вести справочник заключений | `conclusions` | `create` / `read` / `update` (C, R, U) | own_branch | — |
| Просмотр справочников (типы образцов, лаборатории, статусы) | `sample_types`, `labs`, `*_statuses` | `read` (R) | own_branch / all | — |
| Просмотр технического аудита | `history` | `read` (R) | по указанному `entity_id` | — |
| Управление своими уведомлениями | `alerts` | `read`, `mark-read`, `hide` | own | — |

> Регистратор **не имеет доступа** к испытаниям (`tests` — право `—` в
> `../product/role-access-matrix.md`), не управляет пользователями/ролями и не
> ведёт справочники `indicators`/`research_goals` — это зона начальника
> лаборатории (`lab-chief.md`).

## Сценарии

Подробный пошаговый E2E-сценарий — `../frontend/flows/registrator.flow.md`
(видео `../frontend/flows/videos/registrator-full-flow.webm` и
`../frontend/flows/videos/registrator-legacy-import-and-protocol-flow.webm`).

**Сценарий А — импорт направления:**
1. Принимает физические образцы и электронное направление от санитарного врача.
2. Импортирует направление (Excel — построчный машинный формат; JSON — резервный
   способ; либо `.xls` — реальный бланк «НАПРАВЛЕНИЕ проб пищевых продуктов на
   лабораторные исследования») — направление появляется в статусе `draft`,
   образцы — в `pending`.
3. Открывает направление: проставляет типы образцов, назначает каждому образцу
   исследование (`assign-research`).
4. Регистрирует направление целиком (`draft → registered`) — бэкенд предварительно
   проверяет, что у каждого образца заполнены тип и хотя бы одно исследование.
5. Регистрирует каждый образец (`pending → registered`, проставляет `received_at`);
   при обнаружении брака — отклоняет образец (`reject`).
6. После завершения всех исследований и закрытия образцов (см. `lab-chief.md`)
   выделяет завершённые образцы одного направления и формирует протокол с
   заключением из справочника (`../frontend/flows/registrator.flow.md` §16-17,
   видео `../frontend/flows/videos/protocol-preview-flow.webm` — кнопка
   «Предпросмотр», черновой рендер бланка протокола).

**Сценарий Б — ручное создание направления:**
1. Принимает физические образцы без электронного направления.
2. Создаёт направление вручную (статус `draft`).
3. Добавляет образцы из карточки направления (вкладка «Связанные» → «Добавить
   образец»).
4. Далее — идентично шагам 3–6 сценария А.

## Границы (scope)
Регистратор работает **в рамках своего филиала** (`own_branch`): видит и
редактирует направления, образцы, объекты, протоколы и заключения только своего
филиала. Редактирование направлений/образцов возможно только пока запись в
начальном статусе (`draft` / `pending`) — после регистрации изменение полей на
бэкенде запрещено (`PATCH` не может менять `status_id`; переход статуса — только
через командные эндпоинты `POST /{resource}/{id}/{action}`). Доступа к
испытаниям (`tests`) и к операционным действиям других лабораторий/филиалов нет.

> ⚠️ **(уточнить, известное ограничение реализации):** автоматического
> скоупинга по филиалу в списках нет — любой залогиненный пользователь видит
> все записи независимо от `branch_id`; сузить список можно только вручную
> фильтром. RBAC на уровне API отсутствует — авторизация полностью на фронте
> (см. `../frontend/flows/registrator.flow.md` §0 и
> `../frontend/flows/sanitary-doctor.flow.md` §0, п. 4).

## Definition of Done
- Импорт (Excel / JSON / legacy `.xls`) и ручное создание направления работают
  на реальном (не мок) API: направление появляется в `draft`, образцы — в
  `pending`.
- Регистрация направления проходит проверку готовности (тип + исследование на
  каждый образец), иначе возвращается `409` с понятной причиной.
- Брак образца (`reject`) создаёт запись технического аудита и SSE-уведомление
  владельцу направления.
- Создание протокола доступно только для образцов одного направления в статусе
  `completed`, ещё не привязанных к другому протоколу.
- `bun run lint typecheck build` зелёные; сценарий проверен на реальном API —
  см. чек-листы разделов «Направления» и «Образцы» в
  `../product/frontend-user-stories.md`.
