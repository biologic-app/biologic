# ADR: Движок UI рабочих процессов — adopt vs build

- Статус: **Accepted** (консенсус Planner/Architect/Critic; см. `.omc/plans/workflow-ui-engine-mvp-plan.md`).
- Дата: 2026-07-22.
- Контекст требований: `.omc/specs/deep-interview-workflow-ui-engine.md`.
- Связанные документы: сравнительный отчёт `docs/research/2026-07-22-workflow-render-engines.md`
  (питает решение по слою полей), спецификация формата `docs/architecture/2026-07-22-workflow-schema-v2.md`.

Решение о adopt-vs-build берётся **по трём слоям отдельно** (требование спеки R3): рендер полей /
layout экрана / визуальный редактор. Ниже — по каждому слою, затем сквозные инженерные решения
(b)–(f), которые не зависят от выбора библиотеки полей.

---

## 1. Контекст и силы

- Уже существует рабочий прототип (ныне `frontend/src/modules/workflows/`): graph-first движок
  (VueFlow + json-logic) с билдером, раннером и rule-builder'ом. Это **работает** и несёт
  циклы/условия — то, чего form-библиотеки не дают.
- Настоящий риск LIMS лежит не в форме, а в **двусторонней доменной интеграции** (запись
  результатов тестов): требуются атомарность, идемпотентность, корреляция аудита.
- Ограничения: Vue 3.5 + `@nuxt/ui` v4, strict TS, только явные импорты, bun; лицензии —
  коммерчески безопасные; минимум новых тяжёлых зависимостей.

Гейт R3 существует именно чтобы сопротивляться sunk-cost-логике «прототип уже есть — эволюционируем».
Поэтому решение принимается по слоям, с обязательным добросовестным разбором Option B.

## 2. Решение по слоям

### Слой 1 — Рендер полей (`field.type → контрол`)
- **Решение: BUILD** — подтверждено сравнительным отчётом (`…-workflow-render-engines.md`, §4).
  Реальные кандидаты на adopt (JSON Forms, FormKit — MIT, Vue3-нативные) не дают заявленной
  экономии Фазы 4: (a) кастомные Nuxt UI-рендереры всё равно писать (их «из коробки» рендереры —
  под другие киты); (b) дифференцирующие типы `dictionary`/`computed`/`table`-с-доменной-привязкой
  проектно-специфичны и не идут «из коробки» нигде; (c) FormKit repeater (наш `table`) — в платном
  Pro; (d) adopt несёт второй слой абстракции + риск конфликта со strict TS/явными импортами.
  6 примитивов уже рендерятся нативным Nuxt UI (`JournalRunner.vue:325-352`). Это **не sunk-cost**:
  центральный тезис Option B опровергнут фактами отчёта.
- **Заимствуем идею:** JSON Forms `registry+tester` — как образец расширяемого маппинга
  `field.type → компонент` (без ветвлений), но реализуем сами на Nuxt UI.

### Слой 2 — Layout экрана (грид 12 колонок, секции, таблицы)
- **Решение:** **build.** Layout-модель проекта (`Screen → Row → Block{span}`, schema-doc §3)
  проста, декларативна и рендерится CSS-грид + Nuxt UI. Ни одна из рассмотренных библиотек не
  даёт layout, который стоило бы принимать ценой чужой системы вёрстки поверх Tailwind/Nuxt UI.
- **Обоснование:** layout — это ~150 строк рендера грида; adopt здесь несёт больше интеграционного
  трения, чем экономии.

### Слой 3 — Визуальный редактор (граф + грид-редактор экрана)
- **Решение:** **build.** Граф-редактор уже реализован на VueFlow (`JournalBuilder.vue`);
  грид-редактор экрана со слотами (drag между слотами + resize span) — новый компонент на
  HTML5 DnD + CSS Grid. Готовые form-builder'ы (SurveyJS Creator, Form.io builder) — не graph-first,
  несут коммерческие лицензии и чуждый Nuxt UI дизайн-язык. Adopt отклонён по слою редактора.
- **DnD-подход (c):** сначала нативный HTML5 Drag and Drop API + CSS Grid (ноль новых
  зависимостей). Fallback при проблемах перетаскивания/resize — зависимость `vuedraggable@next`
  (через те же ворота). **Отказ от drag-between-slots в пользу дерева-инспектора недопустим** —
  это нарушило бы приёмочные решения R2/R11; дерево-инспектор возможен лишь как дополнение.

### Steelman Option B (добросовестно, как требует гейт)
Сильнейший аргумент за adopt слоя полей: гейт R3 существует, чтобы противостоять sunk-cost, и
Option A тратит бюджет на **коммодити** (таблицы, файлы, вычисляемые поля, валидация — то, что
зрелые библиотеки решают лучше), оставляя наименее проработанной **дифференцирующую** половину
(graph-управляемая оркестрация доменных команд). Взяв слой полей готовым, план мог бы «испарить»
значительную часть Фазы 4 и высвободить силы на слой целостности доменных действий. Честная цена
перехода признаётся: адаптер библиотеки переформатирует **Фазы 3b–4** (не «только внутренности
рендерера»), добавляет второй слой абстракции (наша схема ↔ схема библиотеки) и риск конфликта со
strict TS / явными импортами. Именно поэтому решение слоя 1 вынесено на факты отчёта, а не
предрешено: если отчёт даёт «GO» — Option B принимается для слоя 1 без пересмотра слоёв 2–3.

Option C (готовая платформа SurveyJS/Form.io целиком) — **отклонён** во всех слоях: не graph-first
(наша модель — граф с условиями/циклами), коммерческие лицензии на builder, чуждый Nuxt UI
дизайн-язык, фактический отказ от работающего прототипа.

## 3. Сквозные инженерные решения (не зависят от выбора библиотеки)

### (b) Исполнение доменных действий: backend, не frontend — **DECIDED**
Доменные действия шага исполняются серверной командой `POST /workflow-runs/{id}/execute-step`
(schema-doc §6), а не последовательностью SDK-вызовов на фронте.
- **Драйвер:** фронт-оркестрация не даёт ни атомарности мульти-действий, ни идемпотентности
  ретрая, ни корреляции аудита — доказано по коду (команды `laboratory_workflow` не идемпотентны;
  `grep idempoten` пуст; фронт-последовательность без отката).
- **Альтернатива (фронт-оркестрация)** отклонена несмотря на скорость и переиспользование
  `workflow-commands.ts`: для LIMS полу-применённый шаг или дважды «завершённый» тест — инцидент
  целостности данных.

### (f) Транзакционная граница — **DECIDED (уточнено по коду)**
Публичные методы `WorkflowCommandService` (`commands.py:34-122`) открывают и коммитят
**собственный** UoW, а доменная мутация живёт на уровне репозитория `uow.workflow.<op>()`.
- **Решение:** `execute-step` **композирует `uow.workflow.complete_test/reject_test/…` напрямую
  в своём единственном UoW** + реплика `_publish_events` + `commit`. Публичные методы
  `WorkflowCommandService` **не вызываются и не рефакторятся** — это чище, чем предполагавшийся
  «рефактор транзакционной границы», и лучше соблюдает границу §2.5 плана.
- **Единственное изменение `laboratory_workflow`:** в методы репозитория и хелпер `_add_audit`
  (`repositories.py:1249`) добавляется **опциональный** kwarg `workflow_run_id` (default `None`),
  прокидываемый в создаваемые `ChangeLog` — обратно-совместимо, существующие pytest зелёные.
- **Асимметрия `_publish_events`** (эмитят только register_direction/register_sample/
  reject_sample/reject_research; НЕ complete_test/reject_test/…) **сохраняется как есть**;
  до правок пишутся characterization-тесты нотификаций.

### Корреляция аудита — **DECIDED**
`change_log` получает nullable-колонку `workflow_run_id`; репозиторий уже пишет `ChangeLog`
внутри себя, поэтому корреляция — это проброс kwarg (см. (f)), а не новый механизм.
Трассируемость «какой процесс/шаг породил доменную мутацию» доступна даже без RBAC.

### Идемпотентность и семантика `attempt` — **DECIDED**
Страж `workflow_step_executions` UNIQUE(run_id, node_id, attempt): повтор → `already_applied`
с сохранённым результатом. Раннер различает `applied` / `already_applied` / 409. При прозрачном
сетевом ретрае клиент шлёт **тот же** `attempt`; инкремент — только при осознанном повторе.

### Комментарии/активность — **DECIDED**
Append-only таблица `workflow_run_events` (не мутабельные JSONB-колонки) — устраняет lost-update
при конкурентном append; активность прогона хранится конкурентно-безопасно и индексируемо.

### Вложения — **DECIDED**
`workflow_attachments.data BYTEA` + лимит `APP_WORKFLOW_ATTACHMENT_MAX_MB` (default 10); колонка
`storage` оставляет путь к object storage post-MVP (инфраструктуры blob в репо нет).

### (d) Размещение backend-модуля — **DECIDED**
Плоские DDD-слои `src/{domain,application,infrastructure,presentation}/workflows/` (как `catalogs`),
по направлению консолидации ROADMAP D1 — а не новый `src/contexts/…`. Модели БД — в общей
`src/infrastructure/db/models/`.

### (e) Наследование auth-модели — **DECIDED (осознанный долг)**
`actor_id` приходит в теле команды; командные эндпоинты `laboratory_workflow` уже работают так
(`router.py:452-465`) — `execute-step` **наследует** существующую модель, а не создаёт новую
дыру. RBAC — вне MVP (R13); фиксируется как осознанный долг до RBAC-этапа.

## 4. Последствия
- Сохраняются инвестиции в graph-first прототип; целостность доменных действий переносится на
  сервер (UoW), где ей место.
- Кросс-модульная зависимость `workflows.application → laboratory_workflow.infrastructure`
  (через `uow.workflow`) — уже существующий UoW-атрибут, новый порт не нужен.
- Одна аддитивная Alembic-миграция; правка существующих таблиц ограничена nullable-колонкой
  `change_log.workflow_run_id`.
- Все три слоя = **build** (Option A) по итогам отчёта; Фазы 3b–4 не переформатируются, оценки
  плана в силе. Отчёт послужил доказательной базой, опровергнувшей центральный тезис Option B, —
  гейт R3 отработал как реальная проверка, а не резиновая печать.

## 5. Follow-ups
- RBAC-этап (пост-MVP); object storage для вложений; вынос `engine/` в `shared/` при втором
  потребителе; миграция comments/activity UI на пагинацию по `workflow_run_events`.

---

### Итог
Все три слоя (рендер полей / layout / редактор) = **build** (Option A), обоснованно по
сравнительному отчёту (§4). Сквозные решения (b)–(f) приняты окончательно. Option B и C отклонены
по фактам, а не по привязанности к прототипу.
