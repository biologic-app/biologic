# Biologic LIMS — фронтенд: User Stories, Use Cases, Acceptance Criteria

Документ описывает функциональность фронтенда (`frontend/`, Vue 3 + Nuxt UI + Pinia)
с точки зрения пользователя: **кто**, **что** и **зачем** делает, какие сценарии
поддержаны и по каким критериям фича считается готовой.

Документ составлен по фактическому коду (`src/pages`, `src/modules`, `src/shared`),
а не по предположениям. Каждая фича = одна история (Epic при необходимости разбит на
истории внутри раздела).

### Роли предметной области

Из `permissions.ts` / `auth.api.ts`: **регистратор** (`is_registrar`),
**заведующий лабораторией** (`is_lab_head`), **заведующий филиалом** (`is_branch_head`),
**администратор** (роли и пользователи). Обобщённо — **сотрудник лаборатории** (оператор).

### Сквозное соглашение (применимо ко всем разделам)

- Данные на проводе — **snake_case**, на FE преобразуются через `camelcase-keys`. API-префикс `/api/v1`.
- Доступ к разделам разграничивается через `usePermission().can(resource, action)`.
  **Текущее состояние:** `auth.can()` возвращает `true` всегда — UI-гейтинг (иконки
  замка, `disabled`, тултипы «Нет прав…») реализован, но фактически прав не ограничивает.
  Истории ниже описывают **целевое** поведение; ограничение бэкендом — Out of Scope/Notes.

## 1. Аутентификация и вход

### User Story
Как **сотрудник лаборатории**,
я хочу войти в систему по логину и паролю,
чтобы получить доступ к рабочему пространству LIMS и его модулям.

### Background
Вход — единственная точка входа в приложение; маршрут `/login` (`requiresAuth: false`).
Сессия (`user`, `permissions`) хранится в `localStorage` (`auth:user`, `auth:permissions`)
через `useStorage`, восстанавливается через `/auth/me` + `/user/me/permissions`.
Без рабочего экрана входа сотрудник не может начать работу.

### Use Cases
- **UC-1.1 Успешный вход.** Сотрудник вводит логин и пароль → `POST /auth/login` →
  сессия сохранена → редирект на `dashboard` → toast «Добро пожаловать, {username}!».
- **UC-1.2 Валидация формы (клиент).** Zod-схема: логин 3–64 символа, только
  `[a-zA-Z0-9._-]`; пароль 8–128 символов. Ошибки показываются под полями до отправки.
- **UC-1.3 Неверные учётные данные.** Бэкенд вернул ошибку → toast «Ошибка входа» с
  сообщением из API (или «Неверный логин или пароль»), пользователь остаётся на `/login`.
- **UC-1.4 Показать/скрыть пароль.** Переключатель меняет `type` поля password ↔ text.
- **UC-1.5 «Запомнить меня».** Чекбокс (подсказка «Оставаться в системе до 30 дней»).
- **UC-1.6 Выход.** Пункт меню пользователя → `POST /auth/logout` → `clearSession()`.
- **UC-1.7 Восстановление сессии.** При перезагрузке `restoreSession()` тянет `/auth/me`;
  при ошибке сессия очищается.

### Acceptance Criteria: Вход

#### Happy Path
- [ ] Given введён валидный логин и пароль зарегистрированного пользователя,
      When пользователь нажимает «Войти»,
      Then выполняется `POST /auth/login`, сессия сохраняется в `localStorage`,
      происходит переход на дашборд и показывается success-toast с именем.
- [ ] Given активная сессия в `localStorage`,
      When пользователь перезагружает страницу,
      Then `restoreSession()` подтягивает профиль и права без повторного входа.

#### Edge Cases
- [ ] Given поле пароля скрыто,
      When пользователь нажимает иконку показа пароля,
      Then значение пароля отображается открытым текстом (и обратно по повторному клику).
- [ ] Given логин содержит пробелы по краям,
      When форма отправляется,
      Then логин обрезается (`trim`) перед отправкой.

#### Error Cases
- [ ] Given логин короче 3 символов или содержит недопустимые символы,
      When пользователь пытается отправить форму,
      Then показывается соответствующее сообщение валидации и запрос не уходит.
- [ ] Given бэкенд вернул ошибку авторизации,
      When ответ получен,
      Then показывается error-toast «Ошибка входа» и пользователь остаётся на `/login`.

#### Performance
- [ ] Ответ `/auth/login` обрабатывается без блокировки UI; кнопка показывает `loading`.

### Out of Scope
Реальная серверная проверка прав, 2FA, восстановление пароля, регистрация, срок жизни
токена «30 дней» (чекбокс пока декоративный).

### Notes
`useAuth` — Pinia store; `email`/`status`/`department` для пользователя на FE
синтезируются из `username` (см. `mapUser`). Демо-режим из i18n не подключён к реальной авторизации.

### Definition of Done
- [ ] `bun run lint` / `bun run typecheck` / `bun run build` зелёные
- [ ] Код прошёл review
- [ ] Проверено в staging с реальным `/auth/*`

## 2. Дашборд (сводка лаборатории)

### User Story
Как **сотрудник лаборатории**,
я хочу видеть сводную статистику и график активности за выбранный период,
чтобы быстро оценивать нагрузку и динамику работы лаборатории.

### Background
Маршрут `/dashboard` (стартовая страница, `/` редиректит сюда). Данные грузятся через
`loadDashboardSummary(range, period)` при изменении диапазона дат или периода
(`daily`/...). Состояние гонки запросов защищено `requestSerial`.

### Use Cases
- **UC-2.1 Просмотр сводки.** При входе грузится сводка за последние 14 дней (`HomeStats`, `HomeChart`).
- **UC-2.2 Смена диапазона дат.** `HomeDateRangePicker` → перезапрос данных.
- **UC-2.3 Смена периода агрегации.** `HomePeriodSelect` → перезапрос.
- **UC-2.4 Открытие уведомлений.** Кнопка-колокол (хоткей `N`) открывает слайдовер; бейдж — число непрочитанных.
- **UC-2.5 Запуск тура.** `TourMenu scope="dashboard"` запускает онбординг-тур.
- **UC-2.6 Ошибка загрузки.** При ошибке показывается `UAlert` с текстом ошибки, данные сбрасываются.

### Acceptance Criteria: Дашборд

#### Happy Path
- [ ] Given пользователь открыл дашборд,
      When страница смонтирована,
      Then за период по умолчанию (последние 14 дней, daily) загружается и отображается
      статистика и график; во время загрузки показывается состояние `loading`.
- [ ] Given пользователь меняет диапазон дат или период,
      When новое значение выбрано,
      Then данные перезапрашиваются, и отображается результат только последнего запроса.

#### Edge Cases
- [ ] Given пользователь быстро меняет период несколько раз подряд,
      When приходят ответы,
      Then показывается результат последнего выбора (устаревшие ответы игнорируются по `requestSerial`).

#### Error Cases
- [ ] Given запрос сводки завершился ошибкой,
      When ответ получен,
      Then показывается `UAlert` с сообщением об ошибке, а карточки/график очищаются.

#### Performance
- [ ] Параллельная смена фильтров не приводит к «мерцанию» устаревшими данными.

### Out of Scope
Экспорт дашборда, кастомные виджеты, сохранение выбранного периода между сессиями.

### Notes
`unreadNotifications` берётся из `useSystemNotifications`; график — `@unovis/vue`.

### Definition of Done
- [ ] Линт/typecheck/build зелёные · review · проверка в staging с реальным summary-эндпоинтом

## 3. Направления

### User Story
Как **регистратор**,
я хочу создавать, импортировать и регистрировать направления,
чтобы запускать лабораторный процесс приёмки материала.

### Background
Маршрут `/directions`. Поверх общей CRUD-таблицы (`DictionaryCrudContent`,
конфиг `crudModules.directions`) добавлены: меню «Создать» (вручную / импорт CSV),
массовая регистрация и удаление. Удалять можно только направления в статусе «Черновик».

### Use Cases
- **UC-3.1 Создать вручную.** «Создать → Создать вручную» открывает форму создания.
- **UC-3.2 Импорт CSV.** «Создать → Импортировать CSV» → выбор `.csv` →
  `POST /directions/import` → toast с итогом (добавлено/пропущено; warning при ошибках).
- **UC-3.3 Массовая регистрация.** Выбор строк → «Зарегистрировать» (`register`,
  поле «Комментарий») доступна только для допустимых статусов.
- **UC-3.4 Удаление черновиков.** «Удалить» активна только если все выбранные — «Черновик».
- **UC-3.5 Поиск / фильтры / столбцы / обновление** — см. раздел 13.

### Acceptance Criteria: Направления

#### Happy Path
- [ ] Given у пользователя есть право `directions:create`,
      When он выбирает «Создать вручную» и сохраняет валидную форму,
      Then направление создаётся и появляется в таблице.
- [ ] Given выбран валидный CSV-файл,
      When импорт завершается успешно,
      Then показывается toast «Импорт направлений завершён» с числом добавленных/пропущенных,
      и таблица обновляется.
- [ ] Given выбраны направления в допустимом статусе,
      When пользователь нажимает «Зарегистрировать» и подтверждает,
      Then выполняется команда `register` и записи переходят в зарегистрированные.

#### Edge Cases
- [ ] Given выбраны направления, среди которых есть не-«Черновик»,
      When пользователь смотрит на кнопку «Удалить»,
      Then кнопка заблокирована, тултип поясняет «Удалять можно только … «Черновик»».
- [ ] Given нет прав на создание и на импорт одновременно,
      When открыт навбар,
      Then кнопка «Создать» заблокирована с иконкой замка и тултипом «Нет прав…».

#### Error Cases
- [ ] Given импорт CSV завершился с ошибками парсинга,
      When ответ получен,
      Then toast окрашен как `warning`/`error` и содержит причину; повторный импорт возможен.
- [ ] Given файл не выбран или импорт уже идёт,
      When срабатывает обработчик,
      Then новый импорт не запускается (защита от повторного клика, `importing`).

#### Performance
- [ ] Во время импорта кнопка «Создать» показывает `loading`, поле файла очищается после выбора.

### Out of Scope
Шаблон CSV для скачивания, предпросмотр импорта до отправки, частичный откат импорта.

### Notes
Импорт — `apiUploadRequest` (multipart). Статусные переходы валидируются на FE по `presetKey`/коду статуса.

### Definition of Done
- [ ] Линт/typecheck/build · review · проверка импорта и регистрации на реальном API

## 4. Образцы

### User Story
Как **сотрудник лаборатории**,
я хочу регистрировать, браковать и закрывать образцы,
чтобы вести их жизненный цикл от приёмки до выдачи результата.

### Background
Маршрут `/samples`, конфиг `crudModules.samples`. Массовые команды над выбранными
строками: «Зарегистрировать», «Брак», «Закрыть» (+ «Удалить»). Каждая команда
допустима только для определённых статусов и может требовать ввода полей.

### Жизненный цикл (из конфигурации команд)
- **register** → поля: `received_at` (обяз.), `deadline`.
- **reject** («Брак») → поле `reason` (обяз.).
- **close** (из статуса `analyzed`) → поля `verdict` (обяз.), `comment`.

### Use Cases
- **UC-4.1 Создать образец** (форма CRUD).
- **UC-4.2 Зарегистрировать** выбранные образцы с датой получения и сроком.
- **UC-4.3 Брак** — отметить образцы бракованными с обязательной причиной.
- **UC-4.4 Закрыть** проанализированные образцы с вердиктом и комментарием.
- **UC-4.5 Удалить / поиск / фильтры / столбцы** — раздел 13.

### Acceptance Criteria: Образцы

#### Happy Path
- [ ] Given выбраны образцы в статусе, допускающем регистрацию,
      When пользователь подтверждает «Зарегистрировать» с заполненной датой получения,
      Then команда `register` выполняется и образцы переходят в зарегистрированные.
- [ ] Given образцы в статусе `analyzed`,
      When пользователь нажимает «Закрыть», вводит вердикт и подтверждает,
      Then выполняется команда `close`, показывается toast «Образцы закрыты».

#### Edge Cases
- [ ] Given выбраны образцы в неподходящих для команды статусах,
      When отображается панель действий,
      Then соответствующая кнопка (`canRegister/canReject/canClose`) заблокирована.

#### Error Cases
- [ ] Given в форме «Брак» не указана причина,
      When пользователь пытается подтвердить,
      Then показывается ошибка обязательного поля и команда не отправляется.
- [ ] Given команда завершилась ошибкой бэкенда,
      When ответ получен,
      Then показывается error-toast с заголовком команды и причиной.

#### Performance
- [ ] Массовая команда применяется одним пользовательским действием к N выбранным строкам;
      счётчик выбранного отображается в `UKbd`.

### Out of Scope
Печать этикеток/штрихкодов образцов, маршрутизация между лабораториями.

### Notes
Поля образца включают `mass`, `nomenclature_code`, `batch_code`, `supplier`, ссылки на
тип образца/направление/протокол (`select` с `source`).

### Definition of Done
- [ ] Линт/typecheck/build · review · проверка всех трёх команд на реальном API

## 5. Исследования

### User Story
Как **сотрудник лаборатории**,
я хочу подтверждать, запускать в работу и отклонять исследования и видеть их детали,
чтобы управлять ходом лабораторных исследований.

### Background
Маршрут `/research`, конфиг `crudModules.research`. Команды: «Подтвердить»
(`confirm`, статус `draft`), «В работу» (`start`, статус `ordered`), «Отклонить»
(`reject`, статусы `draft`/`ordered`, обяз. `reason`). Есть модалка деталей
(`ResearchDetailModal`) со связанными образцами (`useResearchSamples`).

### Use Cases
- **UC-5.1 Создать исследование** (поля: образец, цель исследования, лаборатория, …).
- **UC-5.2 Подтвердить** черновики (без доп. полей).
- **UC-5.3 В работу** — перевести подтверждённые (`ordered`) в работу.
- **UC-5.4 Отклонить** с обязательной причиной.
- **UC-5.5 Детали исследования** — открыть модалку с информацией и связанными образцами/историей.

### Acceptance Criteria: Исследования

#### Happy Path
- [ ] Given выбраны исследования в статусе `draft`,
      When пользователь нажимает «Подтвердить»,
      Then выполняется `confirm`, toast «Исследования подтверждены».
- [ ] Given исследования в статусе `ordered`,
      When пользователь нажимает «В работу»,
      Then выполняется `start`, статус меняется на «в работе».

#### Edge Cases
- [ ] Given выбраны исследования в статусах, не входящих в `[draft, ordered]`,
      When отображается кнопка «Отклонить»,
      Then она заблокирована (`canRejectSelectedResearch`).
- [ ] Given открыта модалка деталей у исследования без связанных образцов,
      When пользователь смотрит блок образцов,
      Then показывается корректное пустое состояние.

#### Error Cases
- [ ] Given причина отклонения пуста,
      When пользователь подтверждает «Отклонить»,
      Then показывается ошибка обязательного поля.

#### Performance
- [ ] Команда применяется к множественному выбору за одно действие.

### Out of Scope
Назначение исполнителя, SLA/таймеры, формирование протоколов/заключений из исследования.

### Notes
`useResearchSamples` сейчас содержит демо-данные (history/samples генерируются клиентски) —
проверить замену на реальный источник при интеграции.

### Definition of Done
- [ ] Линт/typecheck/build · review · проверка команд и модалки на реальном API

## 6. Тесты

### User Story
Как **сотрудник лаборатории**,
я хочу запускать тесты в работу, вносить результаты и возвращать их в очередь,
чтобы фиксировать измерения по показателям.

### Background
Маршрут `/tests`, конфиг `crudModules.tests`. Команды: «В работу» (`start`,
статус `queued`), «Результат» (`complete`, статус `in_progress`, поля `value` обяз.,
`norm`, `comment`), «В очередь» (`requeue`, статус `in_progress`), «Отклонить» (`reject`).

### Use Cases
- **UC-6.1 В работу** — взять тесты из очереди.
- **UC-6.2 Внести результат** — `value` (обяз.), `norm`, `comment`.
- **UC-6.3 Вернуть в очередь** тест из работы.
- **UC-6.4 Отклонить** тест.
- **UC-6.5 Поиск / фильтры / столбцы** — раздел 13. (На странице тестов нет кнопки «Создать».)

### Acceptance Criteria: Тесты

#### Happy Path
- [ ] Given выбраны тесты в статусе `queued`,
      When пользователь нажимает «В работу»,
      Then выполняется `start`, toast «Тесты взяты в работу».
- [ ] Given тест в статусе `in_progress`,
      When пользователь вносит «Значение» и подтверждает «Результат»,
      Then выполняется `complete`, toast «Результаты тестов сохранены».

#### Edge Cases
- [ ] Given выбраны тесты не в статусе `in_progress`,
      When отображаются кнопки «Результат»/«В очередь»,
      Then они заблокированы (`canComplete/canRequeue`).

#### Error Cases
- [ ] Given поле «Значение» пустое,
      When пользователь подтверждает «Результат»,
      Then показывается ошибка обязательного поля, команда не уходит.

#### Performance
- [ ] Команды доступны как массовые действия над выбором.

### Out of Scope
Создание тестов вручную из этого экрана, импорт результатов из приборов.

### Notes
`norm` дублирует норму показателя для фиксации фактического значения нормы на момент теста.

### Definition of Done
- [ ] Линт/typecheck/build · review · проверка команд на реальном API

## 7. Справочники

### User Story
Как **администратор/заведующий**,
я хочу управлять справочными данными (объекты, типы образцов, филиалы, врачи,
лаборатории, цели, показатели, заключения, типы протоколов, статусы),
чтобы поддерживать корректность ссылочных данных во всех модулях.

### Background

типовая CRUD-таблица с собственным конфигом полей. Статусы разделены по контекстам:
для направлений / образцов / исследований / тестов.

### Перечень справочников
Объекты, Типы образцов, Филиалы, Врачи, Лаборатории, Цели исследований, Показатели,
Заключения, Типы протоколов, Статусы (4 контекста).

### Use Cases
- **UC-7.1 Выбор справочника** через навигацию (роут хранит `:module`).
- **UC-7.2 CRUD записи** справочника (создать/редактировать/удалить).
- **UC-7.3 Контексты статусов** — переключение «Для направлений/образцов/исследований/тестов».
- **UC-7.4 Поиск / фильтры / столбцы** — раздел 13.

### Acceptance Criteria: Справочники

#### Happy Path
- [ ] Given пользователь открыл `/dictionaries`,
      When страница загружается,
      Then выбирается справочник по умолчанию (`objects`) и грузится его таблица.
- [ ] Given пользователь выбирает другой справочник в навигации,
      When клик произведён,
      Then URL обновляется (`:module`), и грузится соответствующий справочник.

#### Edge Cases
- [ ] Given выбран справочник «Статусы»,
      When открыта страница,
      Then показываются контексты статусов, и можно переключаться между ними.
- [ ] Given в URL передан неизвестный ключ модуля,
      When страница монтируется,
      Then выполняется корректный фолбэк (валидный справочник, без падения).

#### Error Cases
- [ ] Given сохранение записи справочника не прошло валидацию обязательных полей,
      When пользователь отправляет форму,
      Then показываются ошибки полей, запись не сохраняется.

#### Performance
- [ ] Переключение справочников не перезагружает всё приложение (SPA, ленивые роуты).

### Out of Scope
Версионирование справочников, импорт/экспорт справочников (кроме направлений), аудит изменений.

### Notes
Конфиги полей и фильтров — `src/shared/config/crud-modules.ts`. Маппинг ключей справочника →
конфига — `src/modules/dictionaries/config.ts`.

## 8. Доступ: Пользователи

### User Story
Как **администратор**,
я хочу создавать и редактировать учётные записи пользователей и их права,
чтобы управлять составом сотрудников и их доступом.

### Background
Маршрут `/access/users` (`UsersPage`). Таблица пользователей с серверной пагинацией
(`useServerTable`), оптимистичными операциями (`useOptimistic`), модалкой деталей
(`AccessEntityDetailModal`). Поля: username, ФИО, роль (`role_id`), лаборатория
(`lab_id`), флаги `is_registrar/is_lab_head/is_branch_head`. Поддержаны
персональные переопределения прав (`PermissionOverride`) поверх прав роли.

### Use Cases
- **UC-8.1 Создать пользователя** (логин, ФИО, роль, лаборатория, флаги, пароль).
- **UC-8.2 Редактировать пользователя.**
- **UC-8.3 Удалить с возможностью отмены** — оптимистичное удаление + toast «Отменить».
- **UC-8.4 Просмотр прав** пользователя: права роли (`rolePermissions`) + переопределения.
- **UC-8.5 Переопределить право** конкретному пользователю (allow/deny поверх роли).
- **UC-8.6 Навигация внутри раздела «Доступ»** через `AccessNavigation` (Пользователи / Роли).

### Acceptance Criteria: Пользователи

#### Happy Path
- [ ] Given администратор заполнил обязательные поля нового пользователя,
      When он сохраняет форму,
      Then `POST /users` создаёт пользователя, и он появляется в таблице.
- [ ] Given открыта карточка пользователя,
      When загружаются права,
      Then показываются права роли и персональные переопределения.

#### Edge Cases
- [ ] Given администратор удалил пользователя,
      When показан toast с действием «Отменить»,
      Then до истечения таймаута можно восстановить пользователя (повторный `POST /users`).

#### Error Cases
- [ ] Given восстановление (undo) удаления не прошло на бэкенде,
      When приходит ошибка,
      Then строка убирается обратно и показывается error-toast «Не удалось восстановить пользователя».
- [ ] Given загрузка прав пользователя завершилась ошибкой,
      When ответ получен,
      Then состояние прав не ломает страницу (грейсфул-обработка).

#### Performance
- [ ] Список использует серверную пагинацию; операции создания/удаления отражаются
      в UI оптимистично, до подтверждения сервера.

### Out of Scope
Сброс/смена пароля пользователем, блокировка/разблокировка, импорт пользователей.

### Notes
`can()` в `UsersPage` сейчас всегда `true` (см. сквозное соглашение). `password_hash` в
форме — поле передачи пароля при создании.

## 9. Доступ: Роли и права

### User Story
Как **администратор**,
я хочу создавать роли и настраивать матрицу их прав по ресурсам и действиям,
чтобы централизованно управлять доступом сотрудников.

### Background
Маршрут `/access/roles` (`UserTypesPage`, ресурс `user-types`). CRUD ролей +
редактирование набора прав роли (`Permission[]`: `resource` × `action`, опц. `scope`).
Действия: CRUD (`view/create/edit/delete`) и командные (`import/export/register/confirm/
start/complete/close/release/reject/requeue/approve`). Удаление — с undo.

### Use Cases
- **UC-9.1 Создать роль** с названием и набором прав.
- **UC-9.2 Редактировать права роли** (матрица ресурс × действие, `updatePermissions`).
- **UC-9.3 Удалить роль / роли** с возможностью отмены.
- **UC-9.4 Загрузка прав роли** при открытии карточки.

### Acceptance Criteria: Роли и права

#### Happy Path
- [ ] Given администратор создаёт роль и отмечает нужные права,
      When он сохраняет,
      Then роль сохраняется с выбранным набором прав, toast подтверждает успех.
- [ ] Given открыта существующая роль,
      When загружаются её права,
      Then матрица отражает текущие `resource`×`action` роли.

#### Edge Cases
- [ ] Given администратор удалил одну или несколько ролей,
      When показан toast «Роль(и) удалена(ы)» с «Отменить»,
      Then удаление можно отменить до истечения таймаута.

#### Error Cases
- [ ] Given сохранение роли не прошло,
      When приходит ошибка,

- [ ] Given загрузка прав роли упала,
      When ответ получен,
      Then показывается toast «Не удалось загрузить права роли», страница остаётся рабочей.

#### Performance
- [ ] Изменение матрицы прав не требует перезагрузки списка ролей.

### Out of Scope
Иерархия/наследование ролей, шаблоны прав, журнал изменений прав.

### Notes
Бэкендные `roles`/`role-permissions` маппятся в FE-ресурс `user-types` (см. `mapResource`).
Действия нормализуются: `read→view`, `update→edit`, `issue→release`, `result→complete`.

## 10. Системные уведомления

### User Story
Как **сотрудник лаборатории**,
я хочу получать уведомления о событиях системы в реальном времени,
чтобы своевременно реагировать на изменения по моим сущностям.

### Background
`useSystemNotifications` (`src/shared/composables`). Список грузится и обновляется
по **SSE** (`EventSource`) с авто-переподключением (`reconnectTimer`). Непрочитанные
(`read_at === null`) формируют бейдж на колоколе дашборда. Слайдовер уведомлений
открывается кнопкой/хоткеем `N`.

### Use Cases
- **UC-10.1 Получение уведомлений в реальном времени** через SSE (`upsertNotification`).
- **UC-10.2 Бейдж непрочитанных** на иконке колокола.
- **UC-10.3 Открытие списка** уведомлений в слайдовере.
- **UC-10.4 Пометка прочитанным** (переход в `readNotifications`).
- **UC-10.5 Авто-переподключение** при разрыве SSE.

### Acceptance Criteria: Уведомления

#### Happy Path
- [ ] Given пользователь авторизован и SSE-поток активен,
      When приходит новое уведомление,
      Then оно добавляется в начало списка, и счётчик непрочитанных увеличивается.

#### Edge Cases
- [ ] Given приходит уже существующее уведомление (тот же `id`),
      When оно обрабатывается,
      Then запись обновляется на месте, а не дублируется.
- [ ] Given непрочитанных уведомлений нет,
      When отображается колокол,
      Then бейдж со счётчиком скрыт.

#### Error Cases
- [ ] Given SSE-соединение разорвалось,
      When срабатывает обработчик ошибки,
      Then запускается таймер переподключения, и поток восстанавливается без действий пользователя.

#### Performance
- [ ] Используется `shallowRef` для списка; обновления не вызывают лишних глубоких ре-рендеров.

### Out of Scope
Группировка/фильтрация уведомлений, пуш-уведомления браузера, настройки подписок.

### Notes
`SYSTEM_ACTOR_ID` — служебный actor для системных событий. Источник адреса SSE — `buildApiUrl`.

### Definition of Done
- [ ] Линт/typecheck/build · review · проверка realtime-доставки и реконнекта на staging

чтобы быстро понять ключевые элементы интерфейса.

### Background
Туры на `driver.js`. Реестр шагов — `tour.registry.ts` (привязка к `[data-tour="..."]`),
сервис — `tour.service.ts`, состояние пройденности — `tour.storage.ts`. Запуск —
через `TourMenu` (например, `scope="dashboard"`). Шаги привязаны к реальным элементам
(уведомления, диапазон, период, меню тура).

### Use Cases
- **UC-11.1 Запуск тура** из `TourMenu` для текущего scope.
- **UC-11.2 Прохождение шагов** с подсветкой целевых элементов и поповерами.
- **UC-11.3 Пропуск отсутствующих шагов** — шаг показывается только если его элемент есть в DOM.
- **UC-11.4 Запоминание прохождения** (ключ учитывает scope, id, версию, роль).

### Acceptance Criteria: Туры

#### Happy Path
- [ ] Given пользователь на дашборде,
      When он запускает тур из меню,
      Then последовательно подсвечиваются элементы (`data-tour`) с поясняющими поповерами.

#### Edge Cases
- [ ] Given целевого элемента шага нет в DOM,

- [ ] Given версия тура изменилась,

- [ ] Given `document` недоступен (SSR/edge),

      Then код не падает (защита `typeof document === "undefined"`).

#### Performance
- [ ] Тур не блокирует взаимодействие со страницей вне активного шага.

### Out of Scope
Редактор туров в UI, аналитика прохождения шагов.

### Notes

## 13. Сквозной механизм CRUD-таблицы

> Базовый компонент `DictionaryCrudContent.vue`, используемый Направлениями, Образцами,
> Исследованиями, Тестами и всеми Справочниками. Истории 3–7 наследуют эти критерии.

### User Story
Как **сотрудник лаборатории**,
я хочу единообразно искать, фильтровать, листать и редактировать записи в любой таблице,
чтобы работать со всеми разделами по одному предсказуемому паттерну.

### Background
Единый компонент таблицы инкапсулирует: поиск (`CrudSearchControl`), фильтры
(`CrudFilterControls` + `CrudFilterModal`), настройку видимости столбцов
(`columnMenuItems`), обновление по токену (`refreshToken`), сброс (`resetToken`),
множественный выбор (`selectedCount`), контекстное меню строки (`RowContextMenu`),
модалку деталей, создание/редактирование (`openCreate/openEdit`) и оптимистичное
удаление с отменой (`undoDelete`). Команды раскрываются наружу через `defineExpose`.

### Use Cases
- **UC-13.1 Поиск** по таблице (debounced глобальный поиск).
- **UC-13.2 Фильтры** — открыть модалку, применить, увидеть счётчик активных (`activeFilterCount`), сбросить.
- **UC-13.3 Видимость столбцов** — меню «Столбцы таблицы».
- **UC-13.4 Обновление данных** — кнопка refresh (инкремент `refreshToken`).
- **UC-13.5 Множественный выбор** — массовые действия и удаление, счётчик в `UKbd`.
- **UC-13.6 Создание/редактирование** через форму по конфигу полей (`layout.span`, типы: text/number/boolean/date/textarea/select).
- **UC-13.7 Удаление с отменой** — оптимистично убрать строку + toast «Отменить».
- **UC-13.8 Детали и связанные сущности** — `openDetail` / `openRelatedDetail` (directions/samples/research).
- **UC-13.9 Контекстное меню строки** (ПКМ) с доступными действиями.
- **UC-13.10 Скелетоны загрузки** строк (`createSkeletonRows`).

### Acceptance Criteria: CRUD-таблица

#### Happy Path
- [ ] Given пользователь вводит запрос в поиск,
      When ввод стабилизировался (debounce),
      Then таблица показывает отфильтрованные результаты.
- [ ] Given пользователь применил фильтры в модалке,
      When он подтверждает,
      Then данные перезапрашиваются и счётчик активных фильтров отражает их число.
- [ ] Given пользователь сохраняет валидную форму создания/редактирования,
      When он подтверждает,
      Then запись создаётся/обновляется и отражается в таблице.

#### Edge Cases
- [ ] Given результатов нет,
      When таблица отрисована,
      Then показывается пустое состояние (`CrudTableEmptyState`).
- [ ] Given данные ещё грузятся,
      When таблица отрисована,
      Then показываются скелетон-строки, а не пустота.
- [ ] Given выбрана хотя бы одна строка,
      When отображается тулбар,
      Then массовые действия и «Удалить» становятся видимыми со счётчиком в `UKbd`.

#### Error Cases
- [ ] Given удаление записи не прошло на бэкенде,
      When приходит ошибка,
      Then показывается error-toast «Не удалось восстановить/выполнить…», состояние строки откатывается.
- [ ] Given форма содержит невалидные обязательные поля,
      When пользователь сохраняет,
      Then показываются ошибки полей, запрос не отправляется.

#### Performance
- [ ] Список использует серверную пагинацию/таблицу (`useServerTable`); глобальный поиск — с debounce.
- [ ] Удаление отражается в UI немедленно (оптимистично) с возможностью отмены до подтверждения сервера.

### Out of Scope
Экспорт таблиц в файл (кроме импорта направлений), сохранение пресетов фильтров на сервере,
inline-редактирование ячеек.

### Notes
Видимость столбцов и настройки таблицы сохраняются по ключу (`table-settings:…`).
Доступность команд считается через `canRunCommandOnSelection` по статусам строк.

### Definition of Done
- [ ] Линт/typecheck/build зелёные
- [ ] Код прошёл review
- [ ] Поведение проверено как минимум на двух разных модулях (например, Образцы и Справочник)
