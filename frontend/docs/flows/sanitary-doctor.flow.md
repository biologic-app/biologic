# Поток санитарного врача (E2E flow spec)

> Источник: зона ответственности санитарного врача (СВ) в лабораторной
> системе, зафиксированная для написания Playwright e2e-тестов. Написан по
> аналогии с `docs/flows/registrator.flow.md` — теми же маршрутами и
> терминологией, но для read-only роли.
>
> Стенд: backend `http://localhost:8080` (`/api/v1`), frontend
> `http://localhost:5177`. Демо-учётка: `sandoctor` / `sandoctor123`
> (роль `sanitary_inspector`, scope `own_objects`, см.
> `src/shared/config/role-credentials.ts` и
> `backend/migrations/versions/20260303_0009_seed_initial_rbac_users.py`).
>
> Видео: `docs/flows/videos/sanitary-doctor-protocol-view-flow.webm` —
> просмотр протокола, оформленного регистратором в
> `registrator-legacy-import-and-protocol-flow.webm` (§5).

## 0. Зона ответственности и что реально работает

Санитарный врач выезжает на объект, собирает образцы и оформляет
**направление в электронном виде** (во внешней системе или файле — вне
контура этого приложения). Дальше:

1. Доставляет образцы и электронное направление в филиал.
2. **Регистратор импортирует направление** (см. `registrator.flow.md` §2) —
   СВ направления в системе не создаёт.
3. С момента импорта СВ отслеживает статусы своих направлений/образцов
   (`draft → registered → in_progress → completed`, см. «Быстрая справка»
   ниже) и, по готовности, протоколы.
4. Роль полностью **read-only** — просмотр направлений/образцов/протоколов/
   заключений по своим объектам, плюс собственные уведомления.

### Права роли (реальные, с бэкенда)

`GET /auth/login` для `sandoctor` возвращает ровно 5 permission-записей, все
со `scope: "own"`:

| resource | action |
|---|---|
| `directions` | `read` |
| `samples` | `read` |
| `protocols` | `read` |
| `conclusions` | `read` |
| `change_log` | `read` |

Ничего похожего на `create`/`update`/`delete`/`register`/`reject` в матрице
нет (`ROLE_PERMISSION_MATRIX["sanitary_inspector"]` в
`20260303_0009_seed_initial_rbac_users.py`). На фронте это транслируется в
`directions:view`, `samples:view`, `protocols:view`, `conclusions:view`
(маппинг `read → view` в `src/modules/auth/auth.api.ts`).

### Исправлено в этой сессии

Реальный обработчик контекстного меню строки — `getRowActionItems` в
`DictionaryCrudContent.vue` (используется и `/directions`, и `/samples`, и
справочниками). `src/shared/ui/table-actions.ts`/`createActionColumn` —
**мёртвый код**: определён, но нигде не импортируется, к делу не относится.

| # | Проблема | Исправление |
|---|----------|-------------|
| 1 | Пункт «Редактировать» в контекстном меню строки (`getRowActionItems`) не проверял права вообще — рендерился всегда активным. Клик по нему не давал реально редактировать (`useCrudDialog.openEdit` сам молча откатывался в режим просмотра при отсутствии `can(resource,'edit')`), но пункт меню выглядел кликабельным, а не заблокированным — в отличие от «Создать»/«Удалить», для которых уже был паттерн иконки-замка. | `getRowActionItems`: иконка/`disabled` пункта «Редактировать» теперь считаются через `can(props.config.resource, 'edit')`, как у остальных действий. |
| 2 | Пункт «Удалить» в том же меню (`isDeleteAllowed`) проверял только статус сущности (`entityRule.deletableStatuses`), **не проверяя права роли вообще**. Санитарный врач мог реально удалить направление/образец в подходящем статусе через UI, хотя роль задумана read-only — это не косметика, а настоящая дыра. | `isDeleteAllowed` теперь дополнительно требует `can(props.config.resource, 'delete')` — статус проверяется только если право есть. |
| 3 | Кнопка «Редактировать» внутри самой карточки направления/образца (`EntityDetailDialogBase.vue`, открывается через «Просмотр») рендерилась без проверки прав — второй, независимый от `getRowActionItems` вход в тот же `PATCH`. | Добавлен `canEditEntity = can(businessKind, 'edit')`, кнопка теперь `v-if="!editing && canEditEntity"`. |
| 4 | Уведомления о `direction_registered`/`sample_registered`/`sample_rejected` были **широковещательными** — `target_user_id`/`target_role_key` в `NotificationDraft` всегда оставались `None`, поэтому `GET /alerts` отдавал их вообще без учёта того, кто спрашивает. Санитарный врач видел чужие уведомления (и наоборот). | Добавлен паттерн публикатор/подписчик: `EventPublisher` (`src/core/events.py`) доставляет доменные события `WorkflowNotificationSubscriber` (`notifications/application/subscribers.py`), который резолвит владельца через `Direction.created_by` (раньше нигде не проставлялся — теперь пишется при создании/импорте направления из текущей сессии) и целится уведомлением именно в него. `GET /alerts`/`GET /alerts/stream` теперь требуют сессию и отдают только уведомления, нацеленные на текущего пользователя. |

Исправление #1 не меняет поведение для регистратора — у роли `registrar`
есть `directions.update`/`samples.update`. Исправление #2 меняет поведение
и для него: `registrar` тоже не имеет `directions.delete`/`samples.delete`
в матрице (`ROLE_PERMISSION_MATRIX["registrar"]` — только `create`/`update`),
поэтому «Удалить» теперь корректно заблокировано и для регистратора — раньше
по ошибке было доступно (при подходящем статусе строки) любой роли.

### Известные ограничения (не исправлялись — вне объёма этой сессии)

| # | Что заявлено | Что реально происходит сейчас |
|---|---|---|
| 1 | «Своих объектов» — просмотр должен быть ограничен объектами, закреплёнными за СВ. | В БД **нет таблицы**, связывающей пользователя с объектами (`own_objects_scope`/`ActorScope.object_ids` в `src/domain/access_control/scope_policy.py` — единственное место, где это упоминается, и оно нигде не вызывается). Любой залогиненный пользователь видит **все** направления/образцы в списках `/directions`/`/samples` независимо от `object_id`. Единственный практический способ сузить список сегодня — вручную выставить фильтр «Объект» (см. §2). Уведомления теперь целятся в `Direction.created_by` (см. «Исправлено» #4) — это решает узкую задачу «кому написать про это конкретное направление», но это не то же самое, что скоуп по объекту: `created_by` — это автор записи, а не привязка пользователя к объекту. |
| 2 | ~~Просмотр протоколов.~~ **Исправлено** — см. §5: страница `/protocols` теперь есть, СВ открывает карточку/техаудит/связанные образцы read-only. |
| 3 | «Прочитать / скрыть» уведомления. | В `NotificationsSlideover.vue` есть только «прочитано» (`POST /alerts/{id}/mark-read`). Действия «скрыть» нет ни на фронте, ни на бэкенде (`src/contexts/notifications/presentation/router.py` — только `mark-read`). |
| 4 | RBAC на уровне API. | Ни один эндпоинт `laboratory_workflow` не проверяет права запроса — авторизация полностью на фронте (см. коммент в `src/shared/config/user-modes.ts`: «Фаза «фронт сначала»»). Санитарный врач физически может выполнить `POST /directions`/`PATCH`/`DELETE` напрямую через API, минуя UI — фронтовые ограничения (см. §2–§4) это не блокируют. |

## 1. Вход в систему

- Страница `/login`, форма (не быстрый вход по роли).
- Учётные данные: `sandoctor` / `sandoctor123`.
- После логина — редирект на `/dashboard`. Права приходят с бэкендом и сразу
  управляют видимостью пунктов меню (см. §0 таблицу прав).

## 2. Направления — только просмотр

- Страница `/directions` доступна (`directions:view`).
- Кнопка «Создать» **задизейблена** (иконка меняется на замок,
  `createMenuDisabled` в `DirectionsPage.vue` — истинно, т.к. нет ни
  `directions:create`, ни `directions:import`), тултип «Нет прав на создание
  или импорт».
- Контекстное меню строки (`getRowActionItems` в `DictionaryCrudContent.vue`):
  - «Просмотр» — доступно.
  - «Редактировать» — задизейблено (замок), нет `directions:edit` (см. §0,
    исправление #1).
  - «Удалить» — задизейблено (замок), нет `directions:delete` (см. §0,
    исправление #2).
  - Командные действия (REG «Зарегистрировать», REJ и т.д.) — пункты
    **присутствуют в меню**, но задизейблены (та же иконка-замок) —
    `canRunCommandOnRow` проверяет `can(command.resource, command.action)`, а
    ни одно командное право (`register`, `reject`, …) роли не выдано.
- Фильтры (`CrudFilterControls.vue`) работают как обычно, включая select
  «Объект» (`object_id`, источник `/objects`) — практический способ вручную
  сузить список до своего объекта, раз автоматического скоупинга нет (см. §0).
- Полнотекстовый поиск (`crud-search-input`) работает без ограничений.

## 3. Образцы — только просмотр

- Страница `/samples`, `samples:view`.
- Кнопки «Создать» нет вообще (страница отрендерена как для регистратора —
  `entity-rules.ts: samples.createDisabled = true` действует для всех ролей,
  не только для регистратора).
- То же самое контекстное меню — «Просмотр» доступен, «Редактировать»/
  «Удалить» задизейблены.
- Массовые действия (`SelectionActionBar`, «Брак» и т.п.) не появляются —
  чекбоксы выбора строк по-прежнему работают, но панель действий пуста без
  разрешённых команд.

## 4. Карточка направления/образца — просмотр без редактирования

- Открыть строку → «Просмотр» → та же `EntityDetailDialogBase.vue`, что и у
  регистратора, три вкладки:
  - **«Карточка»** — поля видны, кнопки «Редактировать» **нет** (см. §0,
    исправление #1) — только read-only отображение + степпер бизнес-статуса.
  - **«Технический аудит»** — `GET /history?filters={entity_type,entity_id}`,
    доступен без ограничений (change_log.read есть).
  - **«Связанные»** — для направления показывает список образцов; кнопки
    «Добавить образец» нет (`canAddSampleToDirection` требует
    `samples:create`, которого нет).

## 5. Протоколы — просмотр (пункт меню «Protocols»)

- Пункт бокового меню «Protocols» (`canViewProtocols = auth.can("protocols","view")`,
  `sanitary_inspector` имеет `protocols:read`) ведёт на `/protocols`
  (`src/pages/ProtocolsPage.vue`) — тот же список/карточка, что видит
  регистратор (см. `registrator.flow.md` §17), но без кнопки «Создать»
  (её нет ни у кого — протокол создаётся только выделением образцов на
  `/samples`, см. `registrator.flow.md` §16) и без «Редактировать» в карточке
  (нет `protocols:update`, та же проверка `can(businessKind,'edit')`, что и
  везде — см. §0, исправление #1).
- Контекстное меню строки: «Просмотр» доступно, «Редактировать»/«Удалить»
  задизейблены — идентично поведению для направлений/образцов (§2–§3).
- Карточка протокола — те же три вкладки: **«Карточка»** (степпер
  «Создано» → «Выдано»), **«Технический аудит»** (`change_log` по
  `entity_type="protocols"`), **«Связанные»** — список образцов, вошедших в
  этот протокол (`GET /samples?filters={protocol_id}`), read-only.
- Раздел «Справочники» по-прежнему не содержит сами протоколы — там только
  `protocol_types` (справочник *типов* протоколов) и `conclusions`
  (заключения, засеяны типовыми значениями миграцией
  `20260702_0016_seed_conclusions` — см. §6).

## 6. Заключения — через «Справочники»

- Пункт меню «Справочники» виден (хотя бы один дочерний ресурс разрешён —
  `conclusions`).
- Внутри: «Заключения» (`/dictionaries/conclusions`) — открывается, список
  read-only (нет `conclusions:create/edit/delete` → кнопки задизейблены тем
  же `getRowActionItems`/`DictionaryCrudContent.vue`, что и у направлений и
  образцов — тот же компонент рендерит все CRUD-таблицы в приложении).
- «Справочники» открываются как выпадающий пункт с дочерними ссылками
  (`type: "trigger"` + `children` в `MainLayout.vue`) — сам пункт «Справочники»
  рендерится кнопкой-раскрывашкой, а не прямой ссылкой, в отличие от
  «Направления»/«Образцы».
- Остальные пункты справочников («Объекты», «Типы образцов», «Филиалы»,
  «Врачи», «Лаборатории», «Цели исследований», «Показатели», «Статусы»,
  «Типы протоколов») — задизейблены (замок), у роли нет соответствующих
  `*.read` прав.

## 7. Раздел «Исследования» — недоступен

- Пункт меню «Research» в сайдбаре — задизейблен (иконка-замок,
  `canViewResearch = auth.can("research","view")` — ложно, `research.read`
  роли не выдан). Кликнуть нельзя (`disabled`).

## 8. Уведомления

- Панель уведомлений (иконка-колокольчик на дашборде) открывается как у
  любой роли — `data-tour="dashboard-notifications"`.
- Alert-события (`workflow.sample_rejected`, `workflow.direction_registered`,
  `workflow.sample_registered`) целятся в конкретного пользователя — того,
  кто создал направление (`Direction.created_by`), через публикатор/
  подписчик (`EventPublisher` → `WorkflowNotificationSubscriber`, см. §0
  п.4). `GET /alerts`/`GET /alerts/stream` требуют сессию и отдают только
  уведомления, у которых `target_user_id` совпадает с текущим
  пользователем — если СВ сам создал направление (вручную или через
  API/импорт от своего имени), уведомления по нему видит только он, не все
  залогиненные пользователи.
- Живое обновление через SSE (`GET /alerts/stream`), отметка прочитанным —
  `POST /alerts/{id}/mark-read`. Действия «скрыть» нет (см. §0 п.3).

## Быстрая справка: статус-коды

```
DIRECTION: draft → registered → in_progress → partially_completed → completed
SAMPLE:    pending → registered → in_progress → analyzed → completed
           pending/registered/in_progress → rejected
```

## Быстрая справка: маршруты, использованные в потоке

| Действие | Метод/путь |
|---|---|
| Логин | `POST /auth/login` |
| Профиль/сессия | `GET /auth/me` |
| Список/карточка направлений | `GET /directions`, `GET /directions/{id}` |
| Список/карточка образцов | `GET /samples`, `GET /samples/{id}` |
| Список/карточка протоколов | `GET /protocols`, `GET /protocols/{id}` |
| Список заключений | `GET /conclusions` |
| Технический аудит | `GET /history?filters={entity_type,entity_id}` |
| Уведомления (список) | `GET /alerts?status=` |
| Уведомления (поток) | `GET /alerts/stream` (SSE) |
| Отметить уведомление прочитанным | `POST /alerts/{id}/mark-read` |
